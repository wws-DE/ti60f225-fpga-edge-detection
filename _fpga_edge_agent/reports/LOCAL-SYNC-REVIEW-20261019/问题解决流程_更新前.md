# TRACK4-PROBLEM-SOLVING-FLOW-001：项目问题解决流程

- Goal: 按可验证的硬件链路顺序，逐项解决 Ti60F225 V4 图像边缘检测项目的阻塞问题；每项完成后停止，等待用户验收，再进入下一项。
- Current state: 仓库 `main` 与上游提交 `73c3ff48` 一致。项目文档记录了 Ti60F225 DemoBoard V4、SC431HAI 摄像头、DDR3 和 HDMI 的工程状态；自研视频恢复版能显示彩条，DDR 诊断版观察到原始阶段码 `0x1F`，仍无真实相机画面。控制面状态仍为 `WAITING_FOR_HARDWARE_BASELINE`，正式 PostgreSQL 未配置。
- Target state: 从硬件基线、显示、真实相机帧、基础图像算法，到高级功能和发布证据，逐节点形成源码、构建、人工下载、人工观察和验收记录。
- Gap: 目前没有正式确认的硬件基线；真实相机帧尚未进入自研链路；后续算法虽有组件证据，但缺少整机实物验收、性能和长期稳定性证据。
- Assumptions: 只修改 `_fpga_edge_agent/work/` 内的独立副本；原始 HDK、参考工程、IP、约束和历史资料只读；Agent 不替用户下载 FPGA、烧写 Flash 或判断硬件现象。
- Open questions: 实物板卡丝印和器件是否与文档一致；当前连接和工具版本是否仍保持；DDR `0x1F` 的阶段语义、`cal_done` 电平和帧发布条件尚未确认。
- Dependencies: Efinity 2026.1.132、目标 Ti60F225/I3、SC431HAI 模组、J4 MIPI 连接、J2/J3 的 MIPI 1.2 V 档、HDMI 显示器、可用下载器，以及用户提供的人工下载和观察结果。当前工具版本与仓库历史构建证据一致。
- Artifacts and hashes: 当前源码基线为 Git commit `73c3ff48f5cb3ad3cca09a368ce4548f5024084d`；后续每个构建必须登记输入清单、工具版本、日志和 SHA256。

## 处理顺序与逐项验收

### 1. H0：确认硬件、连接和工具基线

- 要解决的问题：文档记录与控制面状态不一致，无法安全判断某个工程、引脚或灯态是否对应当前实物。
- 工作内容：确认板卡型号、FPGA 器件、摄像头模组、接口/排线、供电档位、HDMI 显示器、下载器和 Efinity 版本；确认使用哪个工程作为后续基线。
- 验收证据：用户明确确认实际板卡丝印、器件、相机、J4/J2/J3 连接、显示输出、下载方式和工具版本；基线工程与 commit/SHA256 可追溯。
- 理想效果：后续每次下载和观察都能确定“哪块板、哪只相机、哪份 bit、哪组引脚、哪套工具”，不再出现 V4 与 VF 参考混用或旧版本灯义误读。
- 停止点：收到基线确认后停止，等待用户验收 H0；未确认前不改 RTL、不生成 bit、不进行硬件操作。

### 2. H1：建立 HDMI 显示基线

- 要解决的问题：彩条可见只能证明部分显示路径工作，不能证明分辨率、时序和持续稳定性。
- 工作内容：使用独立显示基线工程核对 HDMI 时序、像素时钟、分辨率和稳定输出。
- 验收证据：显示器识别目标模式；彩条/棋盘图完整、颜色正确、边界稳定，无闪烁、撕裂或随机黑屏，并记录持续观察时间。
- 理想效果：显示链路成为可靠观测窗口；之后出现黑屏或彩条变化时，可以把问题缩小到采集、DDR 或算法，而不是 HDMI 基础时序。
- 停止点：完成一次人工观察后停止，等待用户验收 H1。

### 3. A3-DBG：定位 DDR `0x1F` 与帧发布阻塞

- 要解决的问题：自研版持续彩条，没有真实相机画面；DDR 诊断版只观察到 `0x1F`，`cal_done`、`cal_ready`、`capture_start`、`frame publish` 和 `has_frame` 的真实状态尚未闭合。
- 工作内容：先只读核对 `ddr3_top` 的原生状态输出和 `board_frame_system.sv` 的控制链；必要时按独立设计卡增加最小诊断观测，只引出 `cal_done`、同步后的 `cal_ready`、采集启动、帧完成/发布和故障状态，不盲改 DDR 参数。
- 验收证据：构建输入和差异可追踪；用户下载后提供 Programmer 成功记录、LED/屏幕现象或视频；能区分“DDR 未就绪”“已就绪但没有采集帧”“已采集但没有发布”“已发布但显示读取失败”。
- 理想效果：确认 `cal_done → cal_ready → capture_start → frame complete → frame publish → has_frame` 的实际闭环，屏幕从彩条切换为稳定的真实相机画面，或得到明确且可复现的单一阻塞点。
- 停止点：每次诊断 bit 下载和观察后停止，等待用户验收；没有人工观察不得判定 DDR 或整机通过。

### 4. H2：恢复并验收相机真实视频流

- 要解决的问题：相机虽然可在官方工程中出图，但自研链路的 CSI 帧/行/像素计数、RAW10 解包和 Bayer 相位尚未验证。
- 工作内容：核对相机初始化、复位、参考时钟、CSI 接收、RAW10 打包、帧/行边界和异步 FIFO；将原始或旁路画面送至 HDMI。
- 验收证据：稳定取得相机身份/配置结果；帧计数连续，行列边界正确，旁路画面可重复显示；记录颜色偏绿/偏紫与 Bayer/白平衡设置的对照。
- 理想效果：自研工程能持续显示真实相机画面，遮挡、移动和重新上电后仍能恢复；彩条只在明确的无帧状态出现。
- 停止点：人工验收真实画面后停止，等待确认。

### 5. H3：验收彩色转灰度

- 要解决的问题：灰度 RTL 和参考模型已有证据，但尚未与真实相机帧逐像素/逐帧对照。
- 工作内容：固定 Bayer/色彩输入条件，核对定点权重、位宽、截断和延迟对齐。
- 验收证据：真实画面灰度输出连续稳定，灰度与旁路帧空间位置一致；无明显错行、撕裂或亮度溢出。
- 理想效果：任意稳定输入都能得到位置正确、亮度连续的灰度图，为窗口算法提供可信输入。
- 停止点：人工确认灰度效果后停止。

### 6. H4/H5：验收 Sobel、阈值和分屏

- 要解决的问题：窗口缓存、Sobel 和二值化组件已验证，但真实帧上的坐标、边界和显示模式未验收。
- 工作内容：核对双像素/两行缓存、边界补齐、梯度幅值、阈值和分屏延迟；用直线、棋盘和自然场景观察。
- 验收证据：边缘位置与原图对齐，阈值改变具有单调可见效果，分屏无撕裂，边界行为可解释。
- 理想效果：画面一侧显示原始/灰度图，另一侧显示稳定、连续、位置对应的边缘结果，阈值调整不破坏帧同步。
- 停止点：人工验收后停止。

### 7. A1/A2：验收中值滤波和实时阈值控制

- 要解决的问题：组件和按键代码存在，但板级按键引脚、消抖、饱和范围和旁路效果尚未闭合。
- 工作内容：确认按键映射和复位关系，逐档改变阈值，比较滤波旁路与启用结果。
- 验收证据：按键一次只改变一档；阈值在边界处饱和；噪声点减少而主要边缘保留；长按/抖动不会重复触发异常。
- 理想效果：用户可以稳定切换滤波/显示模式并实时调整阈值，结果可预测、可恢复。
- 停止点：人工验收后停止。

### 8. A3：验收 DDR 帧存储、冻结和恢复

- 要解决的问题：单次显示不等于 DDR 长时间读写正确，冻结/源重处理和带宽也未验收。
- 工作内容：用固定测试图和运动场景验证帧写入、读出、双缓冲、冻结、恢复、CDC 和显示无撕裂。
- 验收证据：多次冻结画面完全一致；解除冻结后恢复新帧；长时间运行无花屏、错帧、撕裂和 AXI/DDR 故障。
- 理想效果：DDR 成为可重复的帧存储服务，冻结画面稳定，恢复后继续正常处理。
- 停止点：人工验收后停止。

### 9. A4：验收完整 Canny

- 要解决的问题：完整 Canny 组件有仿真和综合证据，但真实 DDR 服务、最坏帧率和资源闭合未确认。
- 工作内容：逐级核对高斯、梯度、NMS、双阈值和八邻域滞后；测量处理帧率、延迟、资源和时序。
- 验收证据：阶跃/斜边/噪声图与参考结果一致；真实视频边缘连续；最坏场景下无超时或资源溢出。
- 理想效果：Canny 输出保留真实结构边界，噪声受到抑制，处理链可持续运行并达到记录的性能目标。
- 停止点：人工验收后停止。

### 10. A5：验收彩色叠加

- 要解决的问题：彩色、边缘和标注的坐标/延迟对齐以及 Bayer 颜色正确性未完成实物验收。
- 工作内容：对照原图、灰度图、边缘图和叠加图，检查同一目标的空间和帧序一致性。
- 验收证据：颜色、边缘和标注在运动、换帧、冻结后仍对应同一目标，无拖影和错位。
- 理想效果：用户可同时看到真实彩色场景和清晰、准确的边缘/标注结果。
- 停止点：人工验收后停止。

### 11. A6：完成形状识别与资源闭合

- 要解决的问题：当前识别主要是近似候选，开发主线资源曾超量，任意旋转、遮挡、重叠和准确率未闭合。
- 工作内容：先冻结识别输入和输出契约，再做共享/复用、候选去重、旋转矩形/圆/直线测试、资源和时序闭合。
- 验收证据：正负样本、旋转、遮挡、缺边和重叠场景有统计结果；最终源码对应最终 bit；资源、PNR、STA 和帧率均记录。
- 理想效果：目标被正确识别并稳定标注，误检漏检在预定范围内，工程可在器件资源内持续运行。
- 停止点：人工验收后停止。

### 12. R0：最终交付与回归

- 要解决的问题：目前工程、历史 bit、实验记录和实物结论分散，尚未形成最终交付证据链。
- 工作内容：冻结最终源码/约束/IP/工具版本；执行回归、构建、SHA256 登记、下载和完整演示。
- 验收证据：需求—模块—代码—测试—bit—观察双向可追溯；最终演示可重复；剩余限制和许可证边界明确。
- 理想效果：换一台已配置环境的机器即可按文档复现工程，评审者能明确知道哪些功能已通过、哪些仍是限制。
- 停止点：最终交付验收后结束本轮项目推进。
